1. Purpose and scope

The Kestrel simulator is a web app in which a pilot powers up the KF-07 Kestrel Mk II, flies one mission, and has the result recorded. This document is the single set of requirements the build is checked against.

It covers the simulator as a product (flight rules, cockpit, server, data) and the way it is built and run (tests, pipeline, deployment, monitoring). It does not cover the artwork of the suit, which is reused from the tutorials.

Every requirement has an ID so code, tests and commits can point at it.

Prefix Area
FLT Flight rules (the business logic)
CKP Cockpit (the browser app)
API Server and API
DAT Data
IAM Identity and access
QA Testing
OPS Build, containers, deployment, networking
OBS Observability
DSN Design and repository conventions

"Must" marks a requirement the build fails without. "Should" marks one that can be deferred with a note in the progress log.

4. System overview

The simulator is a browser app that runs the flight, backed by a small API that signs pilots in and keeps the mission log. This is the hybrid architecture chosen for the business logic: rules that run every second live in the browser, and rules that must be trusted or remembered live on the server.

Part Built with Runs on Owns
Flight core TypeScript, pure functions in src/core The pilot's browser Every flight rule in section 5 while a mission is being flown
Cockpit React, TypeScript, Vite GitHub Pages Showing the state and sending orders to the flight core
Kestrel control (kestrel-control) Python, FastAPI One container on a server Sign-in, the roster, the mission log, re-checking every mission it is sent
Database (kestrel) PostgreSQL on Neon Neon Pilots and sorties, with constraints as the last line of defence
Pipeline GitHub Actions GitHub Lint, tests, build and deploy on every change

What a pilot does

  1. Signs in.
  2. Runs preflight: queues subsystem checks on the console and starts the preflight.
  3. Flies Aster retrieval: gives orders that move the suit through the seven phases while the flight core enforces the power budget.
  4. Docks. The cockpit sends the mission to Kestrel control, which re-checks it and writes it to the mission log.
  5. Reads the mission log.

Ground rules

  • The flight core has no React, no network and no storage code in it, so it can be tested without a screen.
  • A screen may decide what to show. It may not decide what is allowed.
  • The server never trusts a result the browser reports. It replays the orders through its own copy of the rules.
  • Out of scope for version 1: Kubernetes, an NGINX balancer in front of several copies, and an MCP server. Their Kestrel details stay in their tutorials.

5. Flight rules (FLT)

These are the rules the business-logic tutorial implements. Each is written so one or more test cases can be derived from it. "New" in the source column marks a rule no tutorial states, added here because the simulator needs an answer.

Preflight

ID Requirement Source
FLT-01 The total draw must be the sum of every load switched on, in kW. With nothing on it is 0 kW. Test Cases R1
FLT-02 Throttling back must take a percentage off the total draw. Throttle back is a whole number from 0 to 100: at 0 nothing is taken off, at 100 the draw is 0 kW. Test Cases R2
FLT-03 A throttle-back value outside 0 to 100, or not a whole number, must be refused with a reason. New (R2 leaves it open)
FLT-04 A total draw of 50 kW or more must take 0 kW from the starter cell. Less than 50 kW must take 5 kW. An empty queue takes none. Test Cases R3, R5
FLT-05 The check queue must report load (sum of queued draws), starter cell (FLT-04) and total draw (load plus starter cell), each to one decimal with the unit kW. Test Cases R5
FLT-06 A preflight must only start for a signed-in pilot. Test Cases, Playwright
FLT-07 The launch order must be refused until a preflight has been started for this mission. New

ID Requirement Source

How the rules behave

ID Requirement Source
FLT-50 Every rule must be a pure function: the same state and order always give the same answer, and the state passed in is never changed. New
FLT-51 A rule must answer with either the new state or a refusal and its reason. A refusal is an ordinary answer, not an exception. New
FLT-52 A refused order must change nothing except the alert. The next accepted order must clear the alert. New
FLT-53 Every change to the flight state must go through one function that takes the state and an order and returns the new state. New
FLT-54 Every order given, accepted or refused, must be appended to the order log with its result. New
FLT-55 The flight rules must exist twice with the same results: in TypeScript in the browser and in Python on the server. New

7. Server and API (API)

Kestrel control is one FastAPI application, titled kestrel-control, listening on port 8000. It has three jobs: sign pilots in, keep the roster, and keep a mission log it can vouch for.

Endpoints

Method and path Who Does Answers
GET /healthz Anyone Says the process is alive 200 {"status":"ok"}
GET /readyz Anyone Says whether the database answers 200 ready, or 503 naming the failed check
GET /version Anyone Gives the release number 200 {"version":"1.0.0"}
GET /status Anyone Names the frame and mission 200 with frame "KF-07 Kestrel Mk II", mission "Aster retrieval"
GET /pilots Tech Lists the roster 200, a page of pilots
POST /pilots Tech Enlists a pilot 201, or 409 "Callsign already taken"
GET /pilots/{pilot_id} Tech, or the pilot themself Shows one pilot 200, or 404 "No such pilot"
GET /missions Signed-in pilot Lists that pilot's missions 200, a page of missions
POST /missions Signed-in pilot Submits a flown mission's order log 201, or 422 when the log does not replay
GET /missions/{mission_id} The pilot who flew it, or a tech Shows one mission 200, 403 or 404

Sign-in adds two endpoints from the FastAPI tutorial: POST /token takes an email and password as form fields and answers with an access token, and GET /pilots/me returns the signed-in pilot.

OPS-01 All work must reach main through a branch and a pull request. Nothing is pushed to main directly. Git Basics, CI
OPS-02 The pipeline must run on every pull request and on main: lint, unit tests, then browser tests (which wait for the first two). All must be required checks. CI
OPS-03 The pipeline must also run alembic upgrade head on an empty PostgreSQL and then alembic check. SQLAlchemy + Alembic
OPS-04 A failing browser test must upload its trace and screenshot. Playwright, CI
OPS-05 The pipeline's token must be read-only by default. Secrets come from GitHub secrets; .env is ignored and .env.example is committed. CI, Git Basics
OPS-06 The API must ship as a container image built from a Dockerfile, with a pinned base image, dependencies installed before the code is copied, and no secret baked in. Docker
OPS-07 Each release must have a version number and an image tagged with it. latest must not be deployed. Cloud Deploy, Kubernetes
OPS-08 The container must have a health check and a restart policy. A release counts as live only once its health check passes. Cloud Deploy, Docker
OPS-09 A deploy must keep the previous release ready, and go back to it automatically if the new one fails its health check. Cloud Deploy
OPS-10 Migrations must be applied before a new release takes traffic (DAT-04). SQLAlchemy + Alembic
OPS-11 The cockpit must be built with npm run build (type check, then bundle) and published to GitHub Pages by the pipeline. React + TypeScript, kestrel-simulator notes
OPS-12 The API must sit behind a proxy that terminates HTTPS and redirects HTTP to HTTPS. The database must not be reachable from the public internet except by the API's own connection. Cloud Deploy, Docker, NGINX
OPS-13 Pushing a version tag should build, publish and deploy that release with no manual step. Cloud Deploy

Observability

ID Requirement Source
OBS-01 The API must log one JSON object per line to standard output with ts (UTC), level, service, msg and a trace_id. Observability
OBS-02 Every response must carry an x-trace-id header matching the log lines of that request. Observability
OBS-03 A recorded mission must log the pilot, the mission code and the result. A refused mission must log the order that failed to replay. Observability, API-02
OBS-04 The API must expose /metrics with request counts by method, route and status, and request duration. Observability
OBS-05 The API should count missions by result (kestrel_orders_total with order and result labels is the tutorial's pattern) and keep label values few. Observability
OBS-06 Two alerts should exist: the service has stopped answering for 1 minute, and more than 5% of requests are failing for 1 minute. Observability
OBS-07 Logs must never contain a secret, token, password or email address. Observability, OpenAPI Design

11. Design and repository conventions (DSN)

The repository is kestrel-simulator on GitHub, and it must be readable by a person or a coding agent arriving cold.

ID Requirement Source
DSN-01 The repository must have main as its default branch, a .gitignore covering .env before the first commit, and a committed .env.example with names and no values. Git Basics
DSN-02 README.md must say what the simulator is, how to run each part, how to get a local sign-in, and which environment variables exist. Git Basics, OpenAPI Design
DSN-03 AGENTS.md must contain: Project (with stack versions), Commands (install, run, test, lint, each exact), Project structure, Code style, Testing, Git workflow, and Boundaries (Always, Ask first, Never). CLAUDE.md contains the single line @AGENTS.md. Agent Files
DSN-04 DESIGN.md and tokens.json must describe the look. Tokens are named for their purpose, not their value. One of the two files is the source and the other is generated from it. Agent Files
DSN-05 Text on its background must reach a contrast of at least 4.5 to 1, and the primary colour on its surface at least 3 to 1. Agent Files
DSN-06 Each feature must have a spec at specs/NAME.md with Goal, Context, Acceptance criteria, Out of scope, Constraints, How to verify, and Open questions. Acceptance criteria must cite the requirement IDs in this document. Agent Files
DSN-07 Commit messages must be imperative and cover one idea each. Branches are named for what they do and are deleted after merging. Git Basics
DSN-08 Screens must use the design tokens only: no hard-coded colour values, and no class names built at run time. Tailwind + shadcn/ui
DSN-09 The cockpit must be React with TypeScript in strict mode, built by Vite, on Node.js 20 or newer. React + TypeScript, Tailwind + shadcn/ui
DSN-10 The cockpit and the API should live in separate top-level folders of the one repository, each with its own install, run and test commands. New
DSN-11 The simulator's look is its own. It need not match the tutorials' palette, and the token file already in the repository stands. kestrel-simulator notes

13. Conflicts and rulings

Topic What the tutorials say Ruling
Two power scales Preflight loads add up to 94 kW and the starter cell cuts in under 50 kW (Test Cases). In flight the reactor budget is 25 kW (Observability, Docker). Both stand. Preflight figures are test-bench loads on the hangar's ground supply; flight figures are reactor power.
Sign-in flow FastAPI teaches a password form and a token the API signs itself. OAuth teaches an identity provider with authorization code and PKCE. Version 1 follows the FastAPI tutorial under the IAM rules. An identity provider is version 2.

One small rented server running the API container behind Caddy, as Cloud Deploy teaches, with no database container because the database is on Neon. It needs an address on a domain you own.
Host names in the story kestrel.test (HTTP, Observability) and kestrel.hangar-7.dev (Cloud Deploy) Both stand: kestrel.test is the hangar network, kestrel.hangar-7.dev is the public address.
New rules in this document FLT-03, FLT-07, FLT-17, the /cockpit route, and the new columns in section 8 are in no tutorial. Accepted.
